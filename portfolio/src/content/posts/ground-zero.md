Now that we are really close to launch, I had to look into the distributed architecture side of deploying our SaaS.

Currently the application is deployed on Railway, and its abstractions do take away a lot of the mental load while building the base features, at least the agentic features that we will provide for our customers.

A very useful part of the application is video editing and generation via a chat with AI.

The feature uses a plethora of APIs, and writing code to serve these requests is no more of a concern than just asking Claude to correct the codebase.

The only concern in building applications now has shifted to handling users and their data. When we ship features this fast, we lose track of how reliable the storage architecture is. This is one of the first major projects I have worked on, it's serving 33 active test users, and it has been a victim of exactly this.

This is honestly the first article I am writing, and it's about the architectural changes I have to make to media storage: specifically, how we store the image and video data generated by our service.

## <span class="sec-num">०१</span>Where we are today

Today, the web service does 3 jobs in one container (yeah, this was genuinely my bad for being fast):

1. **Holds the database**: an SQLite file in the volume.
2. **Holds every video**: uploads → takes → renders, in the same volume.
3. **Runs heavy work**: renders run inside the web process as well.

Everything the web knows sits on one disk that only one deployment can mount. A Railway volume can be mounted on one deployment only, so that means:

1. One replica only
2. No failover
3. A short outage on every deploy
4. Limited render capacity

And every video byte a viewer watches in the app is streamed through the web service, which costs egress and memory.

## <span class="sec-num">०२</span>The change I'm making before launch

The change is simple yet effective: **no service owns a disk anymore.** State lives in Postgres and a bucket, which every replica reaches over Railway's private network, so the web and the worker can each run more than one copy. The rest of the backend doesn't change.

### <span class="sub-num">a)</span>The disk is block storage

A volume is a virtual hard drive attached to one machine (on AWS that's EBS). If two replicas each had their own copy, the copies would drift apart after the first write: user A uploads to replica 1, and replica 2 never sees the file.

<div class="fix"><span class="fix-label">Fix</span><span>Split state by kind.</span></div>

- **Files → object storage** (a bucket). Files are stored under keys like `projects/123/video.mp4` and fetched over HTTP. Any number of machines can read and write them. On AWS this is S3.
- **Rows → a shared database server** (Postgres). It handles concurrent writes from many clients properly, which SQLite can't do across machines.

### <span class="sub-num">b)</span>Jobs are closures in memory

A job runs as a JavaScript function inside the web process with `setImmediate`. This causes two problems:

- Another machine can't pick the job up, because a function in memory can't be sent anywhere.
- If the process crashes or redeploys, the job silently disappears. Nothing sweeps jobs left as “running”, so the user just sees a render stuck forever.

<div class="fix"><span class="fix-label">Fix</span><span>A job queue in Postgres plus a separate worker service. A job becomes data (a type name and a JSON payload) instead of code in memory, and any worker can claim it. This is the “elasticity” idea from my cloud computing course: add workers when the queue is long, remove them when it's short.</span></div>

### <span class="sub-num">c)</span>Some state lives in one process

Several things live only in the web process's memory:

- the publish scheduler (a `setInterval` every 30 s)
- a couple of background sweepers
- a few counters that need to be the same on every copy

With two replicas, both schedulers would post the same scheduled post twice, and each replica would only see its own half of those counters.

<div class="fix"><span class="fix-label">Fix</span><span>Advisory locks in Postgres for the timers, so each tick only the replica holding the lock runs it. The counters move into a Postgres table.</span></div>
